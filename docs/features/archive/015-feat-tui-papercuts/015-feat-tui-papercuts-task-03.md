# Task 03: Clear all filters with the backslash hotkey

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Сегодня фильтры в `top` и ставятся, и снимаются по **текущей колонке сортировки**: `setFilter`
(`top/config_view.go:116-131`) работает с ключом `view.OrderKey`. Из этого следуют две проблемы,
которые эта задача закрывает.

**Первая — фильтр невозможно снять не с той колонки.** Пользователь ставит фильтр на `datname`
(`/` при `OrderKey == 3`), затем стрелками уходит на `usename` и ставит второй. Чтобы снять первый,
нужно вернуться ровно на ту же колонку — а узнать, на какой колонке фильтр, сегодня негде. Нового
способа снять всё сразу нет вообще.

**Вторая — очистка врёт.** Ветка `answer == "\n" || answer == ""` делает
`delete(view.Filters, view.OrderKey)` безусловно и всегда возвращает
`"Filters: regular expression cleared"`. `delete` по отсутствующему ключу — no-op, то есть pgcenter
рапортует об успешной очистке, ничего не удалив. Пока индикатора активного фильтра нет, это почти
незаметно; после Task 5 (постоянный индикатор в командной строке, wave 2) пользователь будет видеть
`[F:datname]` сразу после «regular expression cleared» — и это станет громким багом.

Задача добавляет хоткей `\` (зеркало `/`, которым фильтр ставится), снимающий **все** фильтры
текущего экрана одним действием, делает три сообщения честными и документирует клавишу на экране
справки — единственном месте, где пользователь о ней узнает.

Тексты трёх сообщений зафиксированы user-spec'ом (раздел «Граничные случаи», строки 237-241) и
должны совпадать **посимвольно**:

| Ситуация | Текст |
|---|---|
| `\`, фильтров нет | `Filters: no active filters` |
| `\`, фильтры есть | `Filters: cleared N filter(s)` |
| `/` с пустым вводом на колонке без фильтра | `Filters: no filter on this column` |

Существующий текст `"Filters: regular expression cleared"` в списке не значится и **остаётся**:
user-spec запрещает рапортовать успех, когда ничего не удалено, а не переименовывает успешную
очистку.

Задача самодостаточна и от других задач волны не зависит: её файлы (`config_view.go`,
`keybindings.go`, `help.go`, `config_view_test.go`) в wave 1 никем больше не трогаются. Её
пользовательский эффект «индикатор погас» наблюдаем только после Task 5, но собственный код и тесты
от Task 5 независимы — на стенде (Task 8) проверяется уже вся связка.

## What to do

1. **Ввести общий предикат «фильтр активен» и счётчик активных фильтров** в `top/config_view.go`.
   Имена фиксированы, потому что Task 5 обязан вызывать именно их:

   - `isFilterActive(re *regexp.Regexp) bool`
   - `activeFilterCount(filters map[int]*regexp.Regexp) int`

   Предикат обязан совпадать с тем, по которому `printHeaderCell` (`top/stat.go:902`) рисует `*`
   у имени колонки: `re != nil && re.String() != ""`. Счётчик — обёртка над предикатом,
   пробегающая карту фильтров; на `nil`-карте возвращает `0`. Оба помощника нужны и здесь, и в
   Task 5 (`filterToken` строит индикатор по тому же предикату), поэтому счёт, маркер `*` и будущий
   индикатор физически не смогут разойтись. Обе функции — уровня пакета, не вложенные в обработчик:
   Task 5 живёт в `top/ui.go`, это тот же пакет, но другой файл.

2. **Вынести решение об очистке в чистую функцию** — принимает `view.View`, удаляет все активные
   фильтры **на месте**, возвращает текст сообщения и количество удалённого. Это не украшение:
   `printCmdline` при `g == nil` молча выходит (`top/ui.go:207-210`), поэтому текст, собранный
   внутри gocui-обработчика, из unit-теста ненаблюдаем. Чистое ядро + тонкая обвязка — тот же
   приём, которым в проекте тестируется остальной непроверяемый TUI-код (ADR [009], [010];
   `patterns.md`, «Testable TUI Rendering»), и tech-spec в разделе Solution требует именно его.

3. **Добавить обработчик `clearFilters(config *config)`** в `top/config_view.go` по образцу
   соседей (`switchSortOrder`, `toggleIdleConns`): фабрика, возвращающая
   `func(g *gocui.Gui, _ *gocui.View) error`. Обработчик зовёт чистую функцию, отправляет
   `config.view` на `config.viewCh` **только если что-то было удалено**, и ровно один раз печатает
   сообщение в командную строку.

4. **Исправить ветку очистки в `setFilter`**: если на текущей колонке активного фильтра нет —
   вернуть `"Filters: no filter on this column"` и ничего не удалять; если есть — удалить и вернуть
   прежний текст. Остальные ветки (`ok`, ошибка компиляции regexp) не трогать.

5. **Зарегистрировать хоткей** в `top/keybindings.go` — рядом с `'/'` (строка 60), на view
   `"sysstat"`.

6. **Задокументировать клавишу** в `top/help.go`, в блоке `general actions:`, рядом со строкой про
   `/`.

7. **Тесты** — по TDD Anchor. Существующий `Test_setFilter` (`top/config_view_test.go:333-351`)
   **обновить, а не удалить**: его таблица прогоняется последовательно по одному `config.view`, и
   ровно один её кейс меняет ожидание.

## TDD Anchor

Тесты пишем ДО реализации: пишем → запускаем → убеждаемся что падают → пишем код → убеждаемся что
проходят.

- `top/config_view_test.go::Test_clearFilters_noActiveFilters` — на view без фильтров обработчик
  возвращает `nil`, чистая функция отдаёт текст `Filters: no active filters` и счётчик `0`, карта
  фильтров осталась пустой. Отдельно проверить, что **на `viewCh` ничего не отправлено**.
  ВАЖНО, как именно: канал небуферизованный, поэтому одного неблокирующего `select` с `default`
  ПОСЛЕ вызова недостаточно — если реализация ошибочно отправит, обработчик заблокируется **внутри**
  вызова и до проверки управление не дойдёт: тест не упадёт, а повиснет до таймаута `go test`
  (300 s), и упадёт весь пакет, а не этот кейс. Вызывать обработчик в отдельной горутине и ждать
  его завершения с ограничением по времени:

  ```
  done := make(chan struct{})
  go func() { defer close(done); _ = clearFilters(config)(nil, nil) }()
  select {
  case <-done:                     // не заблокировался — это и проверяем
  case <-time.After(time.Second):
      t.Fatal("handler blocked sending on viewCh with no filters to clear")
  }
  select {
  case <-config.viewCh:
      t.Fatal("unexpected send on viewCh")
  default:
  }
  ```
- `top/config_view_test.go::Test_clearFilters_clearsAll` — два активных фильтра на разных колонках
  (например индексы 0 и 3, ни один из них не равен `OrderKey`, иначе тест не отличает новое
  поведение от старого). Ожидаем текст `Filters: cleared 2 filter(s)`, счётчик `2`, карта пуста, вид
  отправлен на `viewCh` (drain-горутина по образцу `Test_scrollOrthogonalToSort`,
  `config_view_test.go:158-163`).
- `top/config_view_test.go::Test_clearFilters_inPlaceVisibleThroughStoredView` — перед очисткой
  положить текущий вид обратно в `config.views[config.view.Name]`, после очистки убедиться, что
  карта фильтров **сохранённой копии** тоже пуста. Тест ловит реализацию, которая присвоила новую
  карту вместо удаления на месте: заголовок карты общий, и переприсваивание оставило бы у
  сохранённой копии старую карту с фильтрами до следующего переключения экрана.
- `top/config_view_test.go::Test_setFilter` (существующий, 333-351) — кейс `"\n"` теперь ожидает
  `Filters: no filter on this column`, потому что предыдущий кейс `""` уже удалил фильтр. Кейсы
  `"example"`, `""` и `"[0-"` не меняются. Зависимость строк от порядка сделать явной: либо
  комментарием, либо (предпочтительно) разбив таблицу на именованные подкейсы
  `clear-existing` / `clear-absent`, чтобы состояние не передавалось между строками неявно.
- `top/config_view_test.go::Test_activeFilterCount` — таблица на предикат и счётчик: `nil`-карта →
  `0`; пустая карта → `0`; карта с `nil`-значением → `0`; карта с regexp, скомпилированным из
  пустой строки → `0` (совпадение с условием `*` в `printHeaderCell`); две активных записи → `2`.

## Acceptance Criteria

- [ ] Хоткей `\` снимает все фильтры текущего экрана одним нажатием.
- [ ] Три текста совпадают посимвольно: `Filters: no active filters`, `Filters: cleared N filter(s)`,
      `Filters: no filter on this column`.
- [ ] `Filters: regular expression cleared` сохранён и возвращается **только** когда фильтр
      действительно удалён.
- [ ] Ни в одном пути не рапортуется успешная очистка, когда ничего не удалено.
- [ ] Фильтры удаляются **на месте** (`delete` в цикле), карта не переприсваивается — очистка видна
      через `config.views[<имя экрана>]`.
- [ ] При отсутствии фильтров обработчик **не отправляет** ничего на `config.viewCh`.
- [ ] `printCmdline` вызывается ровно один раз на каждом пути исполнения обработчика (конвенция
      `config_view.go:288-290`, `patterns.md` → «printCmdline() — Mutual Exclusion»).
- [ ] Хоткей зарегистрирован на view `"sysstat"`, не глобально (`""`).
- [ ] Клавиша `\` описана в `helpTemplate` (`top/help.go`), выравнивание блока `general actions:`
      не поехало.
- [ ] Счётчик активных фильтров использует тот же предикат, что и маркер `*` в `printHeaderCell`.
- [ ] `Test_setFilter` обновлён, а не удалён; зависимость его кейсов от порядка выполнения либо
      устранена, либо явно задокументирована.
- [ ] `make test` (race + coverage), `make lint`, `make vuln` — зелёные.
- [ ] Изменены только четыре файла задачи: `top/config_view.go`, `top/keybindings.go`, `top/help.go`,
      `top/config_view_test.go`.

**Edge cases:**
- **Фильтров нет** — сообщение `Filters: no active filters`, карта не трогается, на `viewCh` ничего
  не уходит, обработчик возвращает `nil`.
- **`viewCh` небуферизован** (`config.go:28`). В production его читает горутина сбора статистики; в
  тестах — drain-горутина. Отправка в подкейсе «фильтров нет» повесила бы обработчик навсегда, а
  drain-горутина, армированная в этом подкейсе, повесит тест на `wg.Wait()`.
- **Общий заголовок карты.** `viewSwitchHandler` (`config_view.go:241`) сохраняет вид **по
  значению**, поэтому `config.view.Filters` и `config.views[config.view.Name].Filters` — одна и та
  же карта. Удаление на месте видно обеим копиям; переприсваивание новой карты — только текущей, и
  при следующем переключении экрана фильтры «воскреснут».
- **`nil`-карта фильтров.** `view.New()` всегда инициализирует `Filters` непустой картой
  (`internal/view/view.go:49` и далее), но счётчик должен корректно отдавать `0` на `nil` — `len`,
  `range` и `delete` на `nil`-карте безопасны, а тесты имеют право сконструировать вид вручную.
- **Множественные фильтры на одном экране** — штатная ситуация: ключ фильтра берётся из `OrderKey`
  в момент нажатия `/`, поэтому смена колонки сортировки и повторное `/` добавляют вторую запись.
  Именно её и снимает `\`.
- **Фильтры хранятся отдельно для каждого экрана**, `\` чистит только текущий — так и требует
  user-spec («все фильтры **текущего экрана**»).
- **Некорректный regexp** в диалоге `/` — поведение не меняется: ничего не сохраняется, в командной
  строке текст ошибки, ранее поставленные фильтры остаются.
- **Ключ фильтра за пределами текущего списка колонок** (класс issue #99) — эту задачу не касается:
  очистка ходит по ключам карты и по колонкам не индексируется. Проверка границ — забота индикатора
  из Task 5.

**Implementation hints:**
- Готовый разбор задачи — §12 code-research (`12.1` текущий код, `12.2` форма обработчика, `12.3`
  правка `setFilter`, `12.4` хоткей и справка, `12.5` ломающиеся тесты). Расходимся с ним в одном
  месте: решение выносится в чистую функцию, а не собирается внутри замыкания, — иначе тексты
  сообщений из unit-теста ненаблюдаемы (`printCmdline` с `g == nil` молча выходит). Форма обвязки
  остаётся ровно той, что описана в §12.2.
- **Хоткей обязан висеть на `"sysstat"`, а не на `""`.** `execKeybindings` в gocui выполняет
  **каждое** совпадение, а `matchView` для пустого имени возвращает `true` безусловно — глобальная
  привязка срабатывала бы при открытом диалоге, и, что хуже, `onKey` пропустил бы `Editor.Edit`,
  сделав `\` невводимым в регулярных выражениях фильтра.
- **Форма привязки — руна, а не `gocui.Key`.** `\` (0x5C) приходит как `ev.Ch = '\\'`, `ev.Key = 0`
  — в отличие от `Space`. В Go-литерале это `'\\'`.
- Соблюдать конвенцию «`printCmdline` ровно один раз на путь исполнения»: два вызова подряд затрут
  первое сообщение раньше, чем пользователь его прочитает (`config_view.go:288-290`).
- Не переписывать `setFilter` целиком и не менять его сигнатуру: он вызывается из `dialogFinish`
  (`dialog.go:127`), а `dialog.go` в волне 2 редактирует другая задача.
- Комментарии к новым функциям писать в стиле файла: короткое `// FuncName does ...` плюс, где это
  неочевидно, причина (почему удаление на месте, почему не отправляем на `viewCh`).
- Безопасность: новых входных данных задача не принимает — `\` не несёт пользовательского текста, а
  очистка только удаляет записи. Санитизация имён колонок относится к индикатору (Task 5,
  Decision 13) и здесь не нужна.
